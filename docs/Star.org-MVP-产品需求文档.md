# Star.org MVP 产品需求文档（PRD）

版本：v1.0
配套文档：《Star.org MVP 技术需求说明书 v0.2》（本文档定义"做什么"，技术说明书定义"怎么做"）

---

## 1. 产品概述

### 1.1 一句话定位

一个可公开验证的星星登记服务：用户登记一颗真实存在的恒星作为纪念，获得包含真实天文数据的证书和永久链接，任何人都可以自行核实这颗星是否已被他人登记过。

### 1.2 要解决的问题

同类产品（ISR、OSR 等）最大的信任缺口是"无法验证"——用户无从得知自己花钱买的名字有没有被重复卖给别人，也不知道公司倒闭后这份记录是否还存在。Star.org 用公开的登记表解决第一个问题，用去中心化的仓库托管缓解第二个问题。

### 1.3 本版本目标

验证一件事：**"可公开验证"这个差异化卖点，是否能让用户愿意为一份数字证书付费。** 不追求功能完整，追求以最快速度获得真实付费用户的反馈。

---

## 2. 目标用户与使用场景

### 2.1 用户画像

MVP 阶段不做细分，统一面向：在 X（Twitter）上活跃、愿意为有情感意义的数字礼物付费、对"可验证""开源""去中心化"这类叙事有天然好感的用户（技术从业者、开发者社区、以及他们的伴侣/家人）。

### 2.2 核心使用场景（按优先级）

| 场景 | 描述 | 优先级 |
|---|---|---|
| 纪念/悼念 | 纪念逝去的亲人或宠物 | 高——付费意愿最稳定，复购/介绍传播意愿强 |
| 求婚/纪念日 | 求婚、结婚纪念日、异地恋纪念 | 高——传播性强，适合在 X 自然传播 |
| 生日/节日礼物 | 送给伴侣、朋友、家人 | 中 |
| 自我纪念 | 用户为自己登记（人生节点、成就） | 中 |

### 2.3 非目标用户

不面向：期待"官方 IAU 认证"的用户（需在多处明确澄清，避免退款纠纷）；期待可转让/可交易资产的用户（产品定位明确排除这类需求）。

## 3. 用户旅程

```
发现产品（X 内容/搜索）
    ↓
进入落地页，理解"可公开验证"这个差异化卖点
    ↓
点击购买 → 跳转结算页（Lemon Squeezy）
    ↓
填写：登记人姓名 / 可选献词 / 接收邮箱
    ↓
完成支付
    ↓
【等待 1-3 分钟】
    ↓
收到邮件：证书下载链接 + 永久链接页面地址
    ↓
打开永久链接页面，查看/分享（X 分享卡片）
    ↓
（可选）在公开登记表中自行核实记录
```

**关键体验节点：** 用户在"等待 1-3 分钟"这一步最容易产生焦虑（付了钱、没有立刻看到结果）。产品需求上必须在结算完成页明确告知"证书将在几分钟内发送至您的邮箱"，管理预期。

## 4. 功能需求（按页面/触点拆分）

### 4.1 落地页

**必须包含的内容模块（按顺序）：**

1. **一句话价值主张**（例如："每一次登记都可以被公开验证"），避免使用"投资""升值""资产"等词
2. **信任背书区块**：说明登记记录同步至公开仓库，附一个"立即查看登记表"的链接，允许用户在购买前就验证可信度
3. **最新登记展示**：优先展示**最近一条真实登记**，让用户在购买前就看到真实交付物，同时起到社会证明作用。必须包含：
   - 该登记的恒星信息（名称、星座、赤经/赤纬、视星等、距地球）
   - **登记人**（选择匿名展示时显示"匿名登记人"，绝不泄漏姓名）
   - **献词**（如有；献词本身是公开内容，匿名登记也应展示）
   - 登记日期、登记编号，以及指向该登记永久页面的链接
   - SIMBAD 核实链接（与永久页一致）
   - 尚无任何登记时的回退：展示内置示例并**明确标注"（示例数据）"**，不得让访客误以为已有真实登记
4. **购买入口**：单一 CTA 按钮，指向登记页 `/register/`（页内填写姓名/献词/匿名后再去结算）
5. **FAQ 区块**，至少覆盖：
   - 这是否是 IAU 官方命名？（必须清楚回答"否"，说明产品性质是纪念性登记）
   - 我的星星会不会被别人重复登记？（说明公开可验证机制）
   - 登记后可以做什么？（分享链接、下载证书）
   - 是否支持退款？（见 6.3 业务规则）

**不需要的内容（MVP 阶段）：** 用户评价墙、多档价格对比表、账号登录入口。

### 4.2 结算页（由 Lemon Squeezy 提供，产品侧需求为字段设计）

**必填字段：**
- 登记人姓名/称呼（展示在证书和永久页面上，允许填写非真实姓名，如"For Anna"）
- 接收证书的邮箱

**选填字段：**
- 献词/留言（限制字数，建议 100 字以内，避免证书排版问题）
- 是否在永久链接页面匿名展示（默认否，即默认展示登记人姓名）

**结算完成页文案要求：** 明确告知"证书将在几分钟内发送至您的邮箱"，并展示一个"稍后可通过此邮箱找回记录"的说明。

### 4.3 证书（PDF）

**必须包含：**
- 登记人姓名、献词（如有）
- 恒星标识符、坐标、星等、光谱型、距地球光年数
- 登记日期
- 永久链接地址
- 验证说明："可通过以下方式自行核实本记录……"，其中**第一条给出 SIMBAD 天文数据库的查询入口**（见 4.4）


**语气要求：** 庄重、克制，避免营销化措辞；纪念/悼念场景下的证书需要经得起严肃场合（如摆放家中、印出来使用）。

### 4.4 永久链接页面

**必须包含：**
- 恒星公开数据（同证书）
- 登记人姓名（或按用户选择匿名）、献词
- 登记日期
- 分享按钮（针对 X 优化，需正确渲染 OG 卡片）
- 指向公开登记表的验证入口
- **指向 SIMBAD 天文数据库的外链**：让登记人和任何访客可以一键到第三方权威天文数据库查看这颗恒星的完整资料（见下方「SIMBAD 外链」）

**不需要：** 评论区、点赞功能、社交互动功能（MVP 阶段不做社区化）。

#### SIMBAD 外链（第三方核实）

产品最核心的信任基础是"这颗星真实存在、证书上的天文数据不是我们编的"。公开登记表能证明"没被重复登记"，但不能证明"这颗星存在" —— 所以需要一条指向**第三方权威天文数据库**的链接。

- **数据库**：SIMBAD（CDS，斯特拉斯堡天文数据中心），天文学界通用的天体数据库
- **查询方式**：按 HIP 编号查询，链接形如 `https://simbad.cds.unistra.fr/simbad/sim-id?Ident=HIP+32349`
- **回退顺序**：HIP 编号 → HD 编号 → 赤经赤纬坐标（候选库 800 颗星均带 HIP 与 HD，回退逻辑是为将来扩充星表准备）
- **出现位置**：永久链接页的星体数据区（独立一行「天文数据库」）+ 核实步骤第一条；证书 PDF 的核实步骤第一条
- **展示文案**：要写清"确认这颗恒星真实存在、且证书所载赤经/赤纬/视星等与数据库一致"，而不是只放个链接
- **外链属性**：新开标签（`target="_blank"`）并带 `rel="noopener noreferrer"`

### 4.5 公开登记表（面向所有访客，不只是付费用户）

**产品需求：**
- 任何人（无需付费、无需登录）都能浏览已登记的记录，用来验证唯一性——这是产品信任机制的核心，不能设置访问门槛
- 需要有清晰的说明文字，告诉非技术用户"怎么算验证成功"（很多访客不熟悉 GitHub，需要用大白话解释，而不是只丢一个仓库链接）

## 5. 业务规则

### 5.1 定价

MVP 阶段单一价格，不做分层。具体定价参考同类竞品（ISR 常年定价约 $35-50 美元），建议定价 $29 或 ¥199，作为市场测试的初始锚点，后续根据转化率数据调整。

### 5.2 恒星分配规则

- 系统自动分配，用户不能自选具体恒星（MVP 阶段不做"选星"体验，避免增加决策成本导致流失）
- 分配优先从视星等更低（更亮、更接近肉眼可见）的恒星开始，让早期用户获得相对更有"分量"的恒星，作为早期种子用户的隐性福利
- 候选库售罄前需要有库存预警机制（人工监控即可，MVP 阶段不需要自动化补货流程），提前手动扩充候选库

### 5.3 退款政策

- 产品本质是数字化、即时交付的纪念品，非质量问题不支持退款；但需在购买前的 FAQ 中说明清楚，减少纠纷
- 若因系统故障导致重复分配、证书错误等产品方过失，无条件退款或重新处理

### 5.4 隐私规则

- 用户邮箱、真实姓名（如与展示名不同）等隐私信息不进入公开仓库
- 登记人享有"匿名展示"的选择权，需在结算页明确提供该选项，不能默认强制公开真实姓名

---

## 6. 异常场景与边界情况

| 场景 | 产品要求 |
|---|---|
| 支付成功但分配/证书生成失败 | 用户需在合理时间内（建议 24 小时）收到人工跟进邮件，说明处理进度，不能让用户"付了钱却没有下文" |
| 用户拼错献词/姓名要求修改 | MVP 阶段支持人工邮件申请修改（无需做自助修改功能） |
| 恒星候选库售罄 | 落地页需能够临时下线购买入口或显示"补货中"提示，不能让用户支付后才发现无星可分 |
| 用户对"是否为官方认证"产生误解并投诉 | 客服话术需要统一口径：明确、友善地澄清产品性质，不回避、不模糊 |

## 7. 成功指标

| 指标 | 目标（上线 30 天内） |
|---|---|
| 日均订单量 | 2-3 单 |
| 落地页到结算页转化率 | 作为基线数据首次采集，暂不设目标值 |
| 支付成功率 | ≥ 95%（低于此值需排查结算流程问题） |
| 从支付完成到用户收到邮件的时长 | ≤ 5 分钟 |
| 因产品方过失导致的退款率 | ＜ 2% |

## 8. 版本范围声明

### 8.1 本版本（V1）包含

落地页、单一价格购买流程、自动分配、PDF 证书、永久链接页面、公开可验证登记表、邮件通知。

### 8.2 本版本明确不包含（后续版本讨论范围）

- 账号系统、多档定价/订阅
- 实体证书/物流
- AR 找星视频等增值体验
- 任何形式的可转让/可交易权益设计
- 多语言支持
- B 端/API 授权场景

### 8.3 与技术方案的关系

本文档描述的所有功能需求，均以《Star.org MVP 技术需求说明书 v0.2》中定义的全 GitHub 托管架构为实现基础。若产品需求发生变化（如需要实时响应、账号系统等），需同步评估是否触发技术方案第 9 章中提到的架构升级信号。
