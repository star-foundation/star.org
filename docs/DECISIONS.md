# 实现决策记录（与文档的差异及理由）

本文件记录实现过程中对《技术需求说明书 v0.4》《产品需求文档 v1.0》的取舍，
便于后续版本回溯。

## D1. 静态生成器：Jekyll → 自研零依赖构建脚本

- 文档：4.6 提到"Jekyll 根据 /data/registrations/ 生成独立静态页面"。
- 实现：`scripts/build-site.mjs` 读取 `site/` 模板与 `data/` 数据，输出 `_site/`，
  由 GitHub Actions 部署到 Pages。
- 理由：部署方式与产物等价（仍然是 GitHub Pages 上的纯静态站点），
  但去掉了 Ruby/Bundler 依赖链——在本机与 CI 上都不会因为 gem 版本问题卡住上线，
  符合"两周内上线、零运维"的目标。若未来需要 Jekyll 生态的插件，可平滑替换构建步骤。

## D2. 防超卖：concurrency 之外再加一层锁

- 文档：4.2 用 Actions `concurrency` 分组串行化认领流程。
- 实现：保留 `concurrency: star-registration`，并在 `scripts/allocate.mjs` 内增加
  mkdir 原子锁 + 拿锁后重读候选库。
- 理由：`concurrency` 只约束 GitHub 侧触发的运行；本地联调、脚本调用、补单等路径不受其保护。
  加锁后所有路径都不会超卖，也让 TC-ALLOC-03 可以在本地用真实并发进程验证（3 轮）。

## D3. 认领编号（slug）由订单号 HMAC 派生

- 文档：slug 未规定生成方式。
- 实现：`slug = base32(HMAC-SHA256(STARORG_SLUG_SECRET, order_id))[0..10]`；无订单号时用随机值。
- 理由：同一笔订单重复触发（Webhook 重投、用户重复点击支付）会落到同一个 slug，
  认领流程因此天然幂等（TC-ERR-04），既不会给同一用户分配第二颗星，也无需在公开仓库里
  保存订单号或任何隐私信息（满足 TC-REG-03）。

## D4. 匿名认领与证书的关系

- 文档：PRD 4.3 要求证书包含认领人姓名；PRD 5.4 要求匿名展示且真实姓名不进公开仓库；
  技术 4.5 要求证书 commit 进公开仓库。
- 冲突点：证书放在公开仓库里，姓名就必然公开。
- 实现：匿名认领的公开记录、永久页面、OG 图、认领表全部不出现姓名；
  证书仍然印上用户填写的称呼（那是用户自己的凭证），但**公开页面不引用证书链接**，
  仅通过邮件把证书发给本人。链接不可猜测（10 位 base32 ≈ 50 bit）。
- 可配置：`site.config.json → policy.anonymousNameInCertificate = false` 时，
  匿名认领的证书本身也不印姓名（显示"匿名认领人"），适合对匿名要求更严格时使用。

## D5. 隐私字段的机器化校验

- 文档：TC-REG-03 要求"认领记录中不包含邮箱、订单号等隐私信息"。
- 实现：`scripts/verify-registry.mjs` 递归扫描每条公开记录，
  用正则匹配邮箱格式与 `order_id/email/customer_name/phone/address/ip` 等字段名，命中即报错；
  CI 每次推送与每天定时巡检都会执行。
- 理由：把合规红线变成可自动执行的检查，而不是靠人记得。

## D6. 邮件与渲染的可离线运行

- 未配置 `RESEND_API_KEY`/`POSTMARK_TOKEN` 时，邮件写入 `outbox/` 目录（含 .eml/.html/.txt），
  本地即可完整核对邮件内容（TC-MAIL-02 的"无占位符残留"检查就建立在这上面）。
- 无头浏览器统一走 `--host-resolver-rules="MAP * ~NOTFOUND"` 完全离线渲染，
  并在产物落盘后主动结束进程——部分受限环境下 Chrome 完成渲染后不会自行退出，
  否则每次渲染会从秒级退化到分钟级。

## D7. 结算链接与售罄状态

- `LEMON_SQUEEZY_CHECKOUT_URL` 未配置，或候选库 available = 0 时，
  落地页与导航栏的购买入口自动下线并显示"补货中"提示（PRD 6 的售罄要求），
  避免用户付款后才发现无星可分。

## D8. 分配改为均匀随机（原为亮度优先）

- 文档：PRD 5.2 原规定"分配优先从视星等更低（更亮）的恒星开始，让早期用户获得相对更有'分量'的恒星，作为早期种子用户的隐性福利"。
- 实现：改为从所有 `available` 恒星中**均匀随机**抽取一颗。候选库文件本身仍按视星等降序排列，但该顺序只用于浏览展示，不再参与分配决策。
- 随机源：由订单号经 `deterministicDigest()`（HMAC-SHA256）派生摘要，取 48 bit 对可用数量取模得到下标。取 48 bit 后取模，模数 ≤ 800 时偏差量级约 1e-12，可忽略；8 万次抽样验证十分位分布落在 9.89%–10.22%（期望 10%）。
  - 用派生种子而非 `Math.random()` 的原因：同一订单重跑抽到同一颗星，`--force` 重发、灾难恢复、人工补单核对都可复现，也让 TC-ALLOC-06/07 能写成确定性断言。
  - 无订单号（人工补单）或缺少 `STARORG_SLUG_SECRET` 时退化为 `crypto.randomInt` 真随机，属可接受降级。
- 放弃亮度优先的理由：① 结果可预测——越早买越亮，等于给了"抢早"一个可计算的理由；② 把恒星按亮度分出高下，与"随机相遇"的纪念叙事冲突；③ 随机分配对每一位认领人都公平，也免去"为什么他的星比我的亮"这类客服成本。
- **放弃的收益（需知情）**：候选库 800 颗中仅约 278 颗（35%）有专名。因专名星集中在亮端，"亮度优先"实际上同时把最亮**和有名字**的星给了早期用户；改为均匀随机后约六成用户拿到的恒星只有 HIP/HD 编号（如 `HIP-39953`）。若这一损失不可接受，可改为"仅在有专名的恒星中随机"或分层随机，届时需同步修改 PRD 5.2 本节与落地页文案。
- **未受影响的核心承诺**：可公开验证的**唯一性**（一颗星不会被认领两次）与随机分配互不冲突；但不再能解释"为什么是这一颗星"——可验证的是"没有重复"，不是"选取过程可复现"。
- 连带改动：`site/index.html` 两处、`site/register.html`、`site/thanks.html` 的"按亮度顺序分配"表述必须同步改为随机，否则构成对外虚假承诺；`tests/pool.test.mjs` 的亮度排序断言保留（池仍按亮度排列），仅去掉"分配优先级/PRD 5.2"的测试名与理由。

## D9. 双语站点：文案目录 + 客户端切换（默认英文，目标为最终态）

- 需求：默认英文，支持中英切换。
- **URL 策略：客户端切换，URL 不变。** 页面上同时具备默认语言与另一种语言的文案，
  由 `site/assets/js/site.js` 在运行时替换，语言选择记在 `localStorage`。
  代价与前提：切换必须依赖 JS，因此**默认语言必须无 JS 也完整可读**——页面用默认语言
  渲染，另一种语言的目录以 JSON 内嵌在 `<script id="i18n-alt">` 里。
- **文案只有一处来源：`site/i18n/<locale>.json`。** 模板里只写 `{{t.a.b}}`，
  不把界面文案写回 HTML，否则中英必然漂移。原先散在 `site.config.json` 的
  `tagline`/`priceDisplay`/`priceNote`/`soldOutMessage`/`checkoutPendingMessage`/`email.subject`
  一并移入目录，配置里不再保留第二份。
- **键集合强一致，构建即拦截。** `validateCatalogs()` 双向校验：模板引用了但目录缺的键、
  以及目录里没人用的键都会报出来；`renderPage()` 再从**渲染产物**里抽取 `data-i18n` 键
  逐一校验，缺任何一条直接构建失败——避免"页面上有个标题永远切不动"这种隐性残缺。
  在产物上抽而不在模板上抽，是因为部分键是构建期动态拼进属性的
  （`data-i18n="{{entryLabelKey}}"`），模板上看不到真实键名。
- **永久链接：`/s/<slug>/` 为英文 canonical**，另产出 `/zh/s/<slug>/` 中文默认入口，
  `hreflang` 互链、`canonical` 指回前者。既有已分享出去的链接继续可用。
- **证书与邮件按买家语言**：订单链路加 `locale` 字段，缺失回退默认语言。
  `locale` 会写入认领记录——它不是隐私字段（`check-secrets.mjs` 不拦），但是一个有意的公开字段。
- **合规必须按语言分套（否则规则静默失效）。** 中英同处一个 HTML 时，只扫一遍 HTML 会让
  另一语言的声明文本顺带满足本语言的规则。因此：
  1. 另一种语言按 `site/i18n/<locale>.json` 的目录值校验——目录就是内嵌进页面的那份数据；
  2. 默认语言按**构建产物**校验，且校验前先剥掉内嵌目录的 `<script>`；
  3. 声明类规则改为**逐键校验**（`landing.faq.a1`、`landing.footerDisclaimer` 必须各自写出
     完整澄清句），不能跑在"整页文案并集"上。
  后两点是负向测试逼出来的：注入 `"Yes, this is fully official naming by the IAU."` 时，
  原「整页并集」写法仍然报通过。中文原文用全称「国际天文学联合会」而非缩写、且澄清句跨句，
  所以规则同时接受全称与跨句写法。
- **术语表**：`claim`＝认领、`dedication`＝献词、`claim registry`＝公开认领表。
  **英文侧禁止 `name a star` 与 `own/ownership`**——前者正是 PRD 全篇要划清界限的说法，
  而现有英文禁用词表抓不到它。
- **排期顺序约束**：默认语言翻到英文必须是**最后一步**。中英同处一个 HTML，
  提前翻转会让英文访客看到"英文外壳 + 中文正文"的混合页，比纯中文更糟。
  因此分四阶段，已全部完成：
  1. 文案目录 + 切换机制 + 合规分套（6 个页面 + 213 条目录项，键集合两侧强一致）
  2. 数据层 locale 化（`astro.mjs` 的 88 个星座英文名与中英星名、星等/距离/光谱/日期格式，
     `view.mjs` 传递 locale）
  3. 订单 `locale` 字段与证书/邮件/OG 按买家语言渲染
     （`order.mjs` 归一化并只接受 en/zh，`register.mjs` 把 `record.locale` 传给交付物）
  4. 翻转 `defaultLocale` 为 `en`、产出 `/zh/s/<slug>/` 中文入口、hreflang 互链、
     sitemap 收录双语、测试断言改为按目录键取值
- **默认语言的现状**：`site.config.json` 的 `defaultLocale` 已是 `en`，落地页与所有
  页面默认渲染英文；中文由页内切换提供，星页另有 `/zh/s/<slug>/` 中文默认入口。
- **数据值也要双语**：星名、星座、星等、距离、日期这类值**不是静态文案**，
  无法用目录键表达，由构建期按两种语言各算一遍，另一种语言的写法放在
  `data-i18n-alt` 属性里，`site.js` 切换时在原值与它之间来回换。
  漏掉这一层会出现"标签变成中文、值还是 Sirius"的错位。

## D10. 中文字体随仓库内置（替代 CI 安装）

- 背景：证书 PDF 与 OG 图靠无头 Chrome 渲染，而 `ubuntu-latest` 镜像**没有**中文字体。
  原先每次 CI 都 `apt-get install fonts-noto-cjk`（多语言全量版约 60MB）并做缓存。
  两个问题：① 渲染结果依赖"运行环境装过什么字体"，本机与 CI 出的证书可能不同；
  ② 属于一个可以彻底去掉的容器依赖。
- 做法：把裁剪后的字体子集随仓库提交（`fonts//`），渲染时由 `chrome.mjs` 以
  `@font-face` + `file://` 引入（实测 headless Chrome 可用，且不依赖系统 fontconfig 状态），
  模板的字体栈把 `StarOrg Sans` / `StarOrg Serif` 放在最前，因此**始终**使用内置字体。
- **裁剪是必须的，不能直接内置原字体**：简体中文单字重为 Sans 7.9MB / Serif 11.1MB，
  两个字重就是 19MB。按"全部 CJK 统一表意文字"裁剪后为 **12.5MB**。
- **为什么不用更小的 GB2312 子集（仅 3.7MB）**：GB2312 只有 6763 个汉字，
  现代姓名常用字（如「玥」）不在其中，会渲染成方框——对已付款拿到的证书不可接受。
- **已知覆盖边界**：子集覆盖 21,603 个码位，含 ASCII、拉丁补充、常用标点、箭头、
  杂项符号、中文标点、CJK 统一表意文字全量、全角形式。**不含 CJK 扩展 A（U+3400–4DBF）
  与扩展 B**，因此极生僻的姓名用字仍会显示为方框；需要时在 `scripts/fetch-fonts.mjs`
  的 `RANGES` 里加区间（扩展 A 约 +4MB）重新生成即可。
- **可复现与防替换**：`scripts/fetch-fonts.mjs` 把上游固定到具体提交
  （`notofonts/noto-cjk@f8d1575`，不能用 `main`），校验上游 sha256 后裁剪，
  并把产出字节的 sha256 与真实覆盖区间写进 `manifest.json`。
  `node scripts/fetch-fonts.mjs --check` 与 `tests/fonts.test.mjs` 都会校验字节一致性，
  防止字体被静默替换——字体字节已经是交付物的一部分，换掉会直接体现在客户收到的证书上。
- **许可证**：Noto CJK 为 SIL OFL 1.1，`fonts//OFL.txt` 随字体一并提交。
- 副作用（正向）：子集只嵌入用到的字形，证书 PDF 由约 288KB 降到约 226KB，
  也减缓了仓库随每次认领增长的速度。
- **残留的非确定性**：证书里 `code` 元素用等宽字体，仍是 `SFMono-Regular/Menlo/Consolas`
  这类系统字体，不同环境外观可能略有差异。这段文字只含 ASCII（slug、路径），
  影响很小；若要完全确定，可再内置一份等宽字体子集。

## D11. 中文版隐藏：默认只保留英文，中文走隐藏入口

- 需求：站点对外**只保留英文**，中文版不公开；中文仍可用，但只能从"某个特殊页面"进入。
- **开关**：`site.config.json → language.showToggle`（现为 `false`）与
  `language.hiddenEntryPath`（现为 `/zh/`）。`showToggle=true` 时完全回到 D9 的双语行为，
  改动可逆——回归检查覆盖了这一点（切换按钮、内嵌目录、sitemap 收录都会回来）。
- **默认语言页面做到"零中文"**，靠三件事，缺一不可：
  1. **不渲染切换按钮**：模板里的按钮包进 `{{#if showLanguageToggle}}`，六个模板一致；
  2. **不内嵌另一种语言的目录**：`buildAltCatalogScript` 不再注入，`buildJsCatalogScript`
     以 `includeAlt:false` 只内嵌默认语言（`site.js` 的 `jsText()` 本来就按
     `payload.alt || {}` 取值，缺 alt 时自然回退，无需改脚本）；
  3. **剥掉数据值与标题里的另一种语言写法**：`data-i18n-alt`（星名、星等、距离、日期的
     另一种语言写法）与 `<html data-alt-lang data-alt-title>` 由 `stripAltLocaleArtifacts()`
     移除。**第 3 条是实测才发现的**：只做前两条时英文页仍残留中文——因为星名/日期这类
     **数据值不是静态文案**，走不了目录，是构建期按两种语言各算一遍内联在属性里的。
- **中文侧的降级**：`/zh/`（隐藏入口）与 `/zh/s/{slug}/` 仍然生成，但
  `noindex, nofollow`、不进 sitemap、英文页也不再声明 `hreflang="zh-CN"`。
  不写进 robots.txt 的 `Disallow`——robots.txt 是公开文件，写进去等于把隐藏地址告诉所有人，
  且被 Disallow 的路径无法被抓取，`noindex` 反而失效。
- **合规不受影响**：合规扫描对**两种语言**分别校验声明（IAU 澄清、退款政策），
  中文目录仍在，因此 `IAU_DISCLAIMER_ZH` / `REFUND_POLICY_ZH` 依旧通过；
  默认语言的产物校验也照旧。隐藏的是中文的**可达性**，不是它的合规性。
- **顺带修掉的测试脆弱点**：`TC-LP-16/18`、`TC-LP-08/09/11/14/15`、e2e 等用例原先断言
  **写死的中文串**，而英文页之所以"含中文"，恰恰是因为内嵌了中文目录——这些断言实际上
  在测"内嵌目录是否存在"，而不是在测页面内容。现改为经 `copy()` 目录键取值
  （带构建期占位符的键取占位符之前的词干），换语言不再让用例失效。
- 代价：普通访客（含搜索引擎）只会看到英文；中文体验需要知道 `/zh/` 地址。

## D12. 先关公开购买入口：首页改为核心理念页

- 需求：先关掉首页等处的「购买 / 认购」链接与说辞，专注核心理念的完善，并把核心理念做成首页；
  **功能与业务保留**——只是不再对外露出，不是拆掉产品。
- **开关只有一处**：`site.config.json → product.purchaseEnabled`（现为 `false`，
  本机/灰度可用环境变量 `STARORG_PURCHASE_ENABLED=true` 覆盖）。构建期算出两个不同的量：
  - `purchaseOpen = purchaseEnabled && 已配置结算链接 && 未售罄` —— 决定**对外露出**
    （导航里的「认领一颗星」按钮、任何指向 `/register/` 的链接）；
  - `checkoutReady = 已配置结算链接 && 未售罄` —— 仍然决定**认领页自身**能否渲染表单。
  两者必须分开，否则"关入口"会顺手把认领页做成死页。模板里的入口一律包在
  `{{#if purchaseOpen}}` 里，所以重新开启不需要改模板、也不需要改脚本。
- **首页 = 核心理念页**：`site/index.html` 改成理念主视觉（含白皮书卡片）+ 五条理念 + 串联图 + FAQ。
  原先落地页的区块（主视觉卖点 / 信任背书 / 最近一次认领样例 / 认领流程 / 购买区 / 价格）
  整体下线；对应文案键仍留在 `site/i18n/*.json` 里，恢复时可直接复用。
- **`/philosophy/` 保留为首页别名**：同一个模板再渲染一遍（canonical 指回 `/`），
  既满足"理念即首页"，也不让已分享出去的 `/philosophy/` 链接失效。
  好处是理念内容只有一份模板，不会出现双页漂移；代价是产物里多一份同内容页面，
  所以别名**不进 sitemap**，FAQ 里指向理念页的那条链接也改成指本页。
- **`/register/` 关闭期间不进 sitemap、自身 `noindex`、不被任何页面链接**，
  但页面、表单、`checkout-url` 纯函数、订单/证书/邮件链路全部照常生成与工作。
- **首页也不露出 `/registry/` 入口**（导航、页脚、FAQ 内联链接全部拿掉）：
  首页只讲理念，"可自行核实"这条承诺改由**永久页**承担
  （`star.verify2` 仍指向 `/registry/`）。`check-compliance.mjs` 的 `VERIFY_ENTRY`
  随之改为校验 `star.verify2` 的两种语言写法，而不是首页有没有链过去。
  其余页面（永久页 / 404 / 等待页 / 认领页）仍保留认领表入口。
- **FAQ 必须留在首页**：`check-compliance.mjs` 的 `IAU_DISCLAIMER_RENDERED` 与
  `REFUND_POLICY_RENDERED` 校验的是构建产物 `_site/index.html` 是否渲染出 IAU 澄清与退款政策，
  FAQ 是这两段声明的承载处。搬家或删减 FAQ 都会让合规扫描直接失败。
  - 因此首页 FAQ 只渲染 8 条：`q1~q4`（IAU 澄清 / 唯一性 / 认领之后能做什么 / 退款政策）

  - `q5~q7`（付款时效 / 个人信息 / 为什么不能挑星）是购买流程问答：**文案键保留在目录里，
    但公开购买关闭期间不渲染**，恢复购买入口时挂回模板即可。
  - `q1`/`a1` 与 `q4`/`a4` 的键位不能动——合规脚本按固定键名校验；
    未渲染的键也不会进页面的内嵌目录（`buildAltCatalogScript` 只嵌入本页用到的键）。

  只在认领页出现；开关打开但没配结算链接时，构建会给出警告（`npm run check:launch` 同样会报）。
