# Star.org MVP 技术需求说明书

版本：v0.3（全托管方案，无需自建/租用服务器）
目标：最短路径产生首批真实付费订单，验证转化率，零运维成本

---

## 0. 版本变更说明

相较 v0.1，本版本做了以下调整：

- 原方案（Vercel + Supabase）替换为**全 GitHub 托管方案**：GitHub Pages 负责前端与静态数据，GitHub Actions 负责全部后端逻辑，不再需要单独的数据库或函数平台账号
- 补充 **4.9 付款完成后的回站路径**：Lemon Squeezy 托管的支付流程会把客户带离本站，
  而证书是 1-3 分钟后才生成的，因此需要等待页 `/thanks/` 加 Lemon Squeezy 侧三处回站链接
  （确认弹窗 / 收据邮件 / 商品 Links）。这是实测联调时发现的问题——
  客户付款后停在 LS 界面，没有任何路径回到站点查看进度
- 明确排除了两个已评估但否决的选项，理由写入第 9 章：
  - **AWS 最便宜服务器（Lightsail/EC2）**：技术可行，但当前订单量级下运维负担和到期收费风险的成本高于收益，予以否决
  - **数字货币收款**：技术可行，但与运营者当前所在司法辖区的监管红线直接冲突，风险量级高于此前讨论过的任何产品设计问题，予以否决

## 1. 项目背景与目标

### 1.1 背景

Star.org 是一个星星认领产品：用户付费"认领"一颗真实存在的恒星，获得包含真实天文数据的证书和一个永久可分享链接。与传统星星命名机构（ISR、OSR 等）的核心差异在于**可公开验证**——所有认领记录同步到公开 Git 仓库，任何人都可以自行核实是否重复分配。

### 1.2 MVP 目标

- 两周内上线，能够收款
- 单一 SKU，单一价格，不做分层定价
- **全程不租用、不自建任何服务器**，只使用免费或低成本的托管服务拼装
- 明确排除：NFT / 链上存证 / 可转让资产 / 订阅制 / 数字货币收款（见第 9 章）

### 1.3 成功标准

上线后 30 天内，日均产生 2-3 笔订单，验证获客话术和转化路径是否成立。

## 2. 范围定义

### 2.1 MVP 范围内

| 模块 | 说明 |
|---|---|
| 恒星候选库 | 预置一批肉眼可见恒星数据，以 JSON 文件形式存于仓库 |
| 分配与查重 | 支付成功后自动分配一颗未被认领的恒星，防止重复分配 |
| 落地页 | GitHub Pages 单页，展示产品说明 + 购买入口 |
| 支付 | Lemon Squeezy（Merchant of Record），法币结算 |
| 证书生成 | GitHub Actions 自动生成 PDF，含星图与天文数据 |
| 永久链接页 | `star.org/s/{slug}`，Jekyll 静态生成 |
| 公开可验证认领表 | 同一仓库内的 JSON 记录，每次认领对应一次 commit |
| 邮件通知 | Actions 调用邮件 API，发送证书链接 |

### 2.2 明确排除（本阶段不做）

- 用户账号系统（认领记录用邮箱 + 订单号找回即可）
- 多档定价 / 订阅
- 实体证书印刷与物流
- AR 找星视频生成
- 链上存证、NFT、任何形式的可转让权益
- **数字货币收款**（理由见第 9.2 节）
- **自建/租用服务器**（理由见第 9.1 节）
- 多语言（先做单一语种，视目标受众定）
- 移动端 App

## 3. 系统架构总览

```
┌───────────────────────────────────┐
│         GitHub Pages                │  ← 落地页 + 每颗星的永久链接页
│    （Jekyll 静态生成，含结算跳转按钮）  │
└──────────────┬──────────────────────┘
               │ 用户点击购买
               ▼
┌───────────────────────────────────┐
│    Lemon Squeezy（托管结算页）        │  ← 收款、开票、退款全权处理
│         Merchant of Record            │
└──────────────┬──────────────────────┘
               │ Webhook（支付成功事件）
               ▼
┌───────────────────────────────────┐
│   Zapier / Make / Pipedream            │  ← 唯一的"胶水"环节
│  （将 Webhook 转换为 GitHub API 调用）   │     免费额度内可覆盖当前量级
└──────────────┬──────────────────────┘
               │ repository_dispatch
               ▼
┌───────────────────────────────────┐
│         GitHub Actions               │  ← 分配恒星 / 生成PDF / 画OG图
│   （concurrency 分组排队，防止超卖）    │     / 发邮件 / commit记录
└──────────────┬──────────────────────┘
               │ commit 回仓库
               ▼
┌───────────────────────────────────┐
│    GitHub Pages 自动重建             │  ← 新的永久链接页面上线
└───────────────────────────────────┘
```

架构原则：**除 Lemon Squeezy 和 Zapier（用于免自建公司收单资质、免自建 Webhook 接收服务）外，全部功能压缩进 GitHub 生态，不新增任何需要独立账号或独立计费的基础设施。**

## 4. 功能需求详述

### 4.1 恒星候选库

**需求：**
- 从公开天文数据源（Hipparcos 星表）预先筛选一批视星等 ≤ 6.5 的恒星，MVP 阶段先取 500-1000 颗子集，用完再扩容
- 每条记录包含：恒星标识符（HIP/HD）、赤经、赤纬、视星等、光谱型、距离（光年）
- 数据一次性导出为仓库内的 JSON 文件，不需要实时调用外部天文数据库

**存储：** `/data/stars_pool.json`（仓库内静态文件，替代原方案中的数据库表）

```json
{
  "id": "HIP-12345",
  "ra": 123.456,
  "dec": 45.678,
  "magnitude": 4.2,
  "spectral_type": "G2V",
  "distance_ly": 213.7,
  "status": "available"
}
```

### 4.2 分配与查重引擎

**需求：**
- 由 GitHub Actions workflow 执行：读取 `stars_pool.json`，选取一条 `status = available` 的记录，写回为 `assigned`，生成唯一 slug
- **并发安全：** 为处理认领的 workflow 设置 `concurrency` 分组，保证同一时间只有一个认领流程在执行，天然避免两个订单抢到同一颗星
- 若未来订单量上升到 concurrency 排队产生明显延迟，可升级为 GitHub Contents API 的乐观锁机制（基于文件 SHA 版本号做冲突检测），MVP 阶段无需实现

**输出：** 生成 `/data/registrations/{slug}.json`（对应原方案中的 `registrations` 表）

```json
{
  "slug": "a1b2c3",
  "star_id": "HIP-12345",
  "owner_display_name": "For Anna",
  "dedication_message": "献给...",
  "registered_at": "2026-09-20T10:00:00Z"
}
```

**隐私要求：** 用户邮箱和订单号**不得**写入公开仓库，仅在 Actions 的执行环境（run 内存中）短暂流转，用于触发邮件发送后即丢弃。

### 4.3 落地页

**需求：**
- Jekyll/纯静态页面，托管于 GitHub Pages，绑定 `star.org` 自定义域名（CNAME 记录指向 GitHub Pages）
- 结构：产品说明（"公开可验证"差异化卖点）→ **最新认领展示** → 购买按钮（跳转认领页 `/register/`）→ FAQ
- **最新认领展示**：读取认领索引里最近一条记录，复用永久链接页的 `buildStarView()`
  渲染同一套字段（恒星信息、认领人、献词、日期、SIMBAD 链接），并链接到该认领的永久页面。
  匿名单据一律显示"匿名认领人"；无认领记录时回退到内置示例并标注"（示例数据）"。
  注意：**默认 OG 图不跟随最新认领变化**（社交平台会缓存 OG 图，频繁变动会让卡片反复失效），
  仍使用固定的示例内容
- 结算页采集：认领人姓名、可选献词、接收证书的邮箱（本版本由站点认领页 `/register/`
  收集后经 `checkout[custom]` 传入，见 4.9）

**FAQ 必须包含的免责声明：**
> 本认领不构成国际天文学联合会（IAU）官方认可的星体命名，属纪念性质的公开可验证认领服务。

### 4.4 支付与订单处理

**需求：**
- Lemon Squeezy 作为 Merchant of Record：无需自建公司主体即可全球收款，平台代缴增值税/销售税
- Lemon Squeezy Webhook（支付成功事件）→ Zapier/Make 接收 → 调用 GitHub `repository_dispatch` API 触发 Actions workflow
- 触发所需的 GitHub 认证信息（Personal Access Token）存储于 Zapier/Make 平台自身的密钥管理中，不暴露在前端

**订单状态流转：**
```
用户下单 → 支付成功(Webhook) → Zapier转发 → Actions触发
→ 分配恒星 → 生成证书 → 生成OG图 → 写入仓库(commit) → Pages重建 → 发送邮件 → 完成
```

**异常处理：** 若流程中途失败，Actions 运行记录本身即为日志，可在 GitHub Actions 面板直接查看失败原因；MVP 阶段用简单的失败通知（发到自己邮箱）即可，不需要复杂重试队列。

### 4.5 PDF 证书生成

**需求：**
- Actions workflow 中安装 Puppeteer（或等效无头浏览器工具），将 HTML 模板渲染为 PDF
- 证书内容：认领人姓名、献词、恒星标识符、坐标、星等、距离、认领日期、永久链接、验证方式说明
- 验证方式说明的**第一条**给出 SIMBAD 天文数据库查询入口（按 HIP 编号），用于第三方核实"这颗星真实存在"
- 生成的 PDF 作为 Actions 产物之一，commit 进仓库的 `/certificates/{slug}.pdf`，通过 GitHub Pages 直接提供下载链接（无需单独的对象存储服务）

### 4.6 永久链接页面

**需求：**
- 路径：`star.org/s/{slug}`
- Jekyll 根据 `/data/registrations/` 目录下的 JSON 文件，在构建时自动为每条记录生成一个独立静态页面
- 展示：恒星公开数据、认领人姓名（可选择匿名展示）、献词、认领日期
- **SIMBAD 外链（第三方核实入口）**：星体数据区独立一行「天文数据库」，指向
  `https://simbad.cds.unistra.fr/simbad/sim-id?Ident=HIP+<hip>`；核实步骤第一条也用同一链接。
  链接由 `scripts/lib/view.mjs` 的 `simbadUrl()` 统一生成，回退顺序 HIP → HD → 赤经赤纬坐标
  （坐标查询用 `/simbad/sim-coo?Coord=<ra>+<dec>`）。永久页与证书共用同一个 view 对象，
  因此两处的链接必然一致
- 外链一律 `target="_blank"` + `rel="noopener noreferrer"`
- **OG 分享图：** 由 Actions 在生成证书的同一流程中，用脚本静态渲染一张 PNG（而非依赖实时渲染服务），commit 进仓库作为页面的 `og:image`，保证在 X 分享时正常显示卡片
- 页面天然支持基本 SEO（每颗星一个独立可索引页面）

### 4.7 公开可验证认领表

**需求：**
- 复用主仓库的 `/data/registrations/` 目录即可，不需要独立仓库（简化 v0.1 中"独立 GitHub 仓库"的设计）
- README 中清楚说明验证方式：任何人可检索该目录确认某颗恒星是否已被认领

### 4.8 邮件通知

**需求：**
- Actions workflow 最后一步调用邮件 API（Resend/Postmark，均有免费额度）发送证书下载链接和永久链接
- MVP 阶段单一模板即可

### 4.9 付款完成后的回站路径

**背景：** 支付由 Lemon Squeezy 托管，客户付款后进入的是 LS 的界面（确认弹窗 → 收据邮件 →
登录后的订单页），证书却要 1-3 分钟才生成。若不配置回站入口，客户在这段时间里无从知道
"钱付了、证书在路上"，也不知道去哪里看进度——这是本项目实际踩到的问题。

**需求：**
- 站点提供付款完成后的等待页 `/thanks/`：确认收到付款、说明证书生成时长与投递邮箱、
  给出"接下来会发生什么"的步骤说明、提供回站入口与客服邮箱；页面可安全关闭
- 等待页支持从 Lemon Squeezy 接收订单号并展示（仅展示、不存储、不外发），便于客户求助客服
- 该页为购买后过渡页：设 `noindex`，不进入 sitemap
- **Lemon Squeezy 侧必须配置全部三处回站链接**（商品设置内，均支持订单变量
  `[order_identifier]` 等），缺一不可：
  1. **Confirmation modal → Button link**：付款完成、尚在结算页时的确认弹窗
  2. **Receipt → Destination link**：收据邮件里的按钮
  3. **Links**：My Orders 订单页上的链接。My Orders 是 LS 的全局客户账户页、界面不可自定义，
     但官方文档说明"商品配置的 links 会出现在订单页上"，因此必须在商品的 Links 里加一条
- 三处统一指向 `https://www.star.org/thanks/?order=[order_identifier]`
- 兜底路径：证书邮件本身携带永久链接；证书生成失败时运维收到告警。**但不得以兜底替代上述配置**

**验收：** 用测试卡下单后，确认弹窗、收据邮件、订单页三处都能一键回到 `/thanks/`，
且等待页正确显示订单号。

## 5. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 当前订单量级（日均个位数）下，Actions 排队执行完全够用；触发到完成预计 1-3 分钟，非实时但满足"支付后几分钟内收到邮件"的验收标准 |
| 安全 | 支付敏感信息完全由 Lemon Squeezy 托管，己方不接触卡号；GitHub Token、邮件 API Key 等密钥存储于 Zapier/Make 或 GitHub Actions Secrets，不进代码库 |
| 合规 | 落地页与证书文案中不得出现"投资""升值""资产""交易""所有权凭证"等措辞；**不接受任何形式的数字货币/虚拟货币付款**（见第 9.2 节）；不承诺 IAU 官方认可 |
| 可用性 | 无 SLA 承诺，GitHub 基础设施本身可用性较高，MVP 阶段可接受偶发失败 + 人工补救 |
| 数据备份 | 公开仓库本身即是一份天然备份，无需额外配置 |
| 成本 | 全部环节使用免费额度（GitHub Pages/Actions 免费，Zapier/Make 免费档，邮件服务免费额度），仅 Lemon Squeezy 按交易抽成，无固定月费 |

## 8. 验收标准

- [ ] 用户可在落地页完成一次完整支付
- [ ] 支付成功后 5 分钟内收到含 PDF 证书和永久链接的邮件
- [ ] 同一颗恒星在任何情况下不会被分配给两个不同订单（通过连续快速下单测试验证 concurrency 排队生效）
- [ ] 永久链接页面在 X 上分享时正确显示 OG 卡片
- [ ] 仓库中能查到对应的认领记录 commit，且不含用户邮箱等隐私信息
- [ ] 落地页与证书文案中不含违反第 5 章合规要求的措辞
- [ ] 支付渠道仅为法币结算，不存在任何数字货币收款入口

## 9. 已评估并否决的方案（附否决理由）

### 9.1 AWS 最低价服务器（Lightsail/EC2）

**结论：技术可行，MVP 阶段不采用。**

- Lightsail 最低约 $3.50-5/月，EC2 t3.micro 前 12 个月有免费额度，技术上都能支撑当前需求
- 否决理由：
  1. 需要额外运维（系统更新、安全组配置、防攻击），这部分时间成本高于当前订单量级能带来的收益
  2. 免费额度存在"到期陷阱"——EC2 12 个月免费、Lightsail 部分套餐 3 个月免费，到期后容易因疏忽产生持续扣费；GitHub Actions 免费额度是按月刷新，不存在这个问题
  3. 当前日均个位数订单，事件触发式的 Actions 架构完全够用，常驻服务器等于为闲置算力付费
- 升级触发信号：当 Zapier/Make 免费额度不足、或需要真正实时响应时，优先考虑升级到 **AWS Lambda**（同属事件触发模式，每月 100 万次调用永久免费），而非直接上服务器

### 9.2 数字货币收款

**结论：技术可行，明确排除，不作为后续版本的升级方向。**

- 技术上可通过 Coinbase Commerce / BTCPay Server / NOWPayments 等服务快速接入，与现有 Webhook → Actions 架构可无缝衔接
- 否决理由：
  1. 运营者当前所在司法辖区将"法定货币与虚拟货币兑换业务"明确定性为非法金融活动，且已有真实判例（涉案金额远低于预期营收规模的个人也曾因此获刑）
  2. 该风险与此前讨论过的"产品要不要设计成可转让资产"是完全不同性质的问题——不是产品设计层面的监管定性风险，而是"收款动作本身"直接对应现行禁止性规定和刑事判例
  3. 对当前"两周内获得生活费"的目标没有正向帮助：Lemon Squeezy 已解决无需注册公司即可全球收款的问题，加入数字货币通道只会增加不必要的风险敞口，且币价波动不利于需要确定金额、快速变现的应急资金需求
- 如未来确有面向 Web3 原生用户的商业理由，需重新评估的前提是：收款主体与结算完全置于境外，运营者本人不直接经手法币与虚拟货币的兑换环节，且需专业律师具体设计架构，不在本文档讨论范围内
