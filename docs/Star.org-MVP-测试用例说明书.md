# Star.org MVP 测试用例说明书

版本：v1.0
依据文档：《Star.org MVP 技术需求说明书 v0.2》《Star.org MVP 产品需求文档 v1.0》

---

## 1. 测试目标

验证 MVP 全流程（落地页 → 支付 → 分配 → 证书生成 → 永久链接 → 登记表验证 → 邮件通知）在真实使用场景下功能正确、数据一致、不出现超卖和隐私泄露。

## 2. 测试范围

覆盖技术方案第 4 章全部功能模块，以及第 5 章非功能需求中可测试的部分（并发安全、隐私合规、合规文案）。不包含性能压测（当前订单量级无此必要）、不包含多语言测试（本版本单一语种）。

## 3. 测试环境要求

- 使用 Lemon Squeezy 的 Test Mode（沙盒环境），避免真实扣款
- 使用独立的测试用 GitHub 仓库或测试分支，避免污染正式登记表
- 准备至少 3 个不同的测试邮箱，用于验证邮件送达与查重场景
- 恒星候选库测试阶段建议只放 5-10 条记录，便于快速测出"售罄"边界情况

## 4. 测试用例

### 4.1 恒星候选库与分配引擎

| 用例编号 | 描述 | 前置条件 | 测试步骤 | 预期结果 | 优先级 |
|---|---|---|---|---|---|
| TC-ALLOC-01 | 正常分配一颗可用恒星 | 候选库中存在 status=available 的记录 | 触发一次完整下单流程 | 系统分配一颗 available 状态的恒星，写回为 assigned，生成唯一 slug | P0 |
| TC-ALLOC-02 | 连续两次独立下单，验证不会分配到同一颗星 | 候选库中至少有 2 条 available 记录 | 依次完成两笔独立订单 | 两笔订单分配到不同恒星，均正确标记为 assigned | P0 |
| TC-ALLOC-03 | **并发下单防超卖测试（核心用例）** | 候选库中仅剩 1 条 available 记录 | 在极短时间内（间隔 <5 秒）模拟触发两个 Actions workflow（可用两个测试订单几乎同时提交） | 仅有一笔订单成功分配到该恒星，另一笔应等待 concurrency 排队后判定"无可用恒星"并进入异常处理流程（见 TC-ERR-01），不允许两笔订单同时拿到同一颗星 | P0 |
| TC-ALLOC-04 | 候选库售罄场景 | 所有恒星均为 assigned 状态 | 触发下单流程 | 系统正确识别无可用恒星，不生成分配记录，触发异常告警（人工可见） | P1 |
| TC-ALLOC-05 | slug 唯一性 | 已存在若干条注册记录 | 连续生成多个 slug | 所有 slug 互不重复 | P1 |

## 7. 测试优先级说明与执行建议

- **P0 用例必须在上线前全部通过**，无一例外，尤其是 TC-ALLOC-03（防超卖）和 TC-REG-03（隐私字段），这两项一旦失败会分别导致产品信任基础崩塌和隐私事故
- **P1 用例建议上线前完成**，允许个别已知问题带入首个迭代周期跟进修复
- **P2 用例可在上线后第一周内补测**，不阻塞上线

## 8. 测试完成标准

- 全部 P0 用例通过
- P1 用例通过率不低于 90%，未通过项有明确的修复计划
- TC-ALLOC-03 需至少执行 3 轮独立测试，确保并发排队机制稳定生效，不存在偶发超卖
- 测试过程中产生的所有测试数据（订单、登记记录）已从正式环境/仓库中清理，不与真实用户数据混淆
